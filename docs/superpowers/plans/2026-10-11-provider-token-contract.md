Baseline: `093aa266e58c7cb03d24315221810b6a14930da6`, separate `Taxonomy-jms-acceptance` worktree. Native implementation by the existing JMS owner; no subagents, remote mutations, live providers or additional heavy reactor while Demo owns its window. ## 1. Complete immutable Responses contract

Add `taxonomy-analysis/src/main/java/com/taxonomy/analysis/service/OpenAiResponsesTokenContract.java` only for the explicit adapter and pinned snapshot in the design. Start with behavioral tests in `OpenAiResponsesTokenContractTest`: the full authored Unicode prompt must survive the immutable user-role input; count and generation must contain exactly identical model/input; generation must contain the configured real output cap and `store:false`; unknown adapter/provider/model and invalid input/output/model-context bounds must fail before any transport. No assumed framing constant or character/token ratio is permitted. Strict count parsing must reject wrong object, fractional/negative/overflow count, duplicates, trailing data, unknown fields, and a count above the configured input bound. Complete response parsing must require the actual Responses object/status/output structure and reject refusal/incomplete output. These are behavior assertions against real serialized JSON, not reflection/file-existence tests.

The initial public seam is an immutable prepared request plus count-validation method; it receives a complete `TokenBudget` and prompt, never JMS or credential data. Internal endpoint selection is derived from the validated configured OpenAI base URL rather than permitting arbitrary cross-provider count endpoints. A production endpoint override is not introduced for this task; loopback fixture transport can route the actual fixed provider URL through the bounded JDK HTTP implementation without changing authority.

## 2. Physical gateway integration

Extend `OpenAiCompatibleGateway` at its existing replay-before-admission boundary. TPM-off follows the old path without body/endpoint/fingerprint changes. For supported active TPM, freeze the prepared body once, execute a count attempt through `LlmRequestAdmission.execute(budget, ...)` and `LlmTransportMeter.exchangeCount` (UNKNOWN only), validate its complete count, then execute generation through a separate ordinary admitted physical operation. Use the existing bounded retry policy for both endpoints; each retry has a new durable physical debit/START and count/generation share the logical invocation only as diagnostics. Count failures must never be recorded as a semantic result, repair output or saved checkpoint answer. Cancellation after count validation must be checked immediately before the fresh generation admission and at its confirmed transport boundary.

Add real loopback HTTP tests in `OpenAiResponsesQuotaGatewayTest`: both actual request paths and complete bodies, per-attempt admitted/started ordering, count and generation retry cases, exhausted 429 cooldown, cancellation during and between operations, missing/lost-confirmation authority producing zero HTTP, wrong count producing zero generation, replay producing zero HTTP, and TPM-off preserving the exact old Chat Completions request. Reuse the existing public quota/permit ports with deterministic observers for early owner tests; add actual broker admission cases to the App test in step 5.

## 3. Usage and semantic authority

Extend `LlmTransportMeter` usage parsing to recognize actual Responses usage (`input_tokens`, `output_tokens`, `total_tokens` and corresponding cached/reasoning details) without interpreting `response.input_tokens` count output as inference usage. Tests invoke real meter exchanges with fixture HTTP bodies: count remains UNKNOWN; known Responses usage remains exact; malformed/negative/overflow/duplicate/totals mismatch does not refund; cached/reasoning values are metadata rather than subtraction/addition guesses. Old Chat and Gemini test fixtures retain their behavior.

Add optional startup quota configuration to `LlmProviderConfig` through its existing host composition. Append the adapter version, pinned model, actual Responses endpoint, complete input schema, configured input bound and actual output cap to the existing public configuration fingerprint only when TPM is active. Test `captureProviderBinding`/`withRequestProvider` against an actual built-in plugin lease: different bound/cap/adapter/model must reject frozen resume; TPM-off must be byte-identical. The gateway and configuration fingerprint must use the same contract validator, so an enabled wire cannot disagree with admitted semantics.

## 4. Genuine automatic HA acceptance

Add `ArtemisAnalysisHaTest` in the App Artemis test package. Use the production factory and the same `ArtemisAnalysisConnection` across disposable persistent shared-store primary/backup brokers with actual advertised connector topology and `ha=true`. The installed Artemis version is 2.53.0; use [its own failover documentation](https://github.com/apache/artemis/blob/2.53.0/docs/user-manual/client-failover.adoc) and [HA transaction contract](https://github.com/apache/artemis/blob/2.53.0/docs/user-manual/ha.adoc). Existing same-server reconnect and fresh-client shared-store takeover are prerequisites, not substitutes.

Behavior tests must retain a confirmed debit, cooldown, unknown TPM reservation and occupied concurrency permit across automatic backup activation, then prove the same production objects reject overspending and cannot manufacture/reseed capacity. A transaction interrupted by failover has zero provider callback until a fresh confirmed admission. A retained worker task redelivers after loss without repeating a committed semantic effect. Use stable deadlines/latches and broker/connection state, not sleeps to infer authority. A fixture failing before the behavior assertion is setup evidence, not RED. External replicated/quorum/TLS/failback HA remains explicitly separate deployment evidence.

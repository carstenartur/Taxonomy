# Native QEA file acceptance and operator evidence

This procedure separates three results: the installed plugin's HTTP/file contract,
behavior with an operator-supplied EA template, and evidence recorded outside this
harness by a person running Enterprise Architect. None is silently promoted into
another. The existing StrictDoc/Archi product-driver inventory remains unchanged.

The reader profile `sparx-qea@1` keeps its separate packaged acceptance. The writer
profile `sparx-qea@2` uses the ordinary integration operation and public
`BASED_FILE_EXPORT_V1` contract. PCS publication is a different operation and still
requires a trusted, verified provider contract.

## 1. Required installed-plugin check

The existing CI plugin-packaging lane owns:

```bash
./mvnw -B verify -Pplugin-packaging-tests,ci-plugin-packaging
```

`ExternalPluginPackagedIT.externalSparxQeaV2JarExportsReviewedFilesAndRetainsDownloadsAcrossPluginChanges`
builds the real optional plugin independently, installs it into the unchanged
packaged host and uses authenticated HTTP. It covers both output modes, an actual
local element edit, original GUIDs on update, independent new identities, exact
mode/basis replay binding, explicit review before download, raw download hashes,
retained-basis reuse and completion after process restart. The same persisted
database is then reopened with a changed plugin artifact and finally without the
plugin. Open reviews must reject execution while completed files, history and
architecture remain readable. File delivery must not advance the observation or
common synchronization checkpoint.

Default QEA inputs are synthetic fixtures generated by the standalone plugin's
tests. The resulting `taxonomy-build/target/sparx-file-export-evidence.json` always
records `realProductStatus: NOT_EXECUTED`. Its `harnessStatus` can become `PASSED`
only after the entire HTTP lifecycle succeeds. Its hashes describe the actual
basis and downloaded bytes, not a reconstructed JSON approximation.

### Browser controls

The browser fixture exercises the production template, translations, CSS, API
wrapper and controls in Chromium. It checks uploaded and retained bases, review
before download, and the German mobile layout. Its transport is a fixture; the
installed-host lifecycle above checks the real HTTP behavior separately.

```bash
./mvnw -B -pl taxonomy-tooling -am test -Dtest=JavascriptContractTest \
  -Dsurefire.failIfNoSpecifiedTests=false -Dtaxonomy.javascript.mode=browser \
  -Dtaxonomy.javascript.sources=.github/scripts/integrations.browser.test.mjs
```

## 2. Use an operator-supplied real template

Use an empty, consistent QEA project from your authorized EA installation, or
obtain a starter template directly from [Sparx's repository resources](https://sparxsystems.com/resources/repositories/).
No proprietary template is committed to this repository or included in the plugin.
The official public starter inspected on 2026-11-06 was:

| File | SHA-256 |
|---|---|
| `eabase-1558-qea.zip` | `1907da778e7f5b2a1d1f30c6b07430b1473fd05135778b30318e27aea686615e` |
| Its `EABase.qea` | `12e5395ccee5b2c5810d0c8fb1d6c810ca57f59b5f7329849f7d2c9af86db4aa` |

That file contains a single empty root package but no `ProjectGUID`; it needs the
separate `NEW_PROJECT` template path. These observations concern that exact file,
not every EA template or version. Inspecting its schema does not mean a writer's
output has been opened in EA. Public availability is not a licence to relabel the
template as MIT; keep operator-provided files and resulting projects out of public
CI artifacts unless their distribution is separately permitted.

With the same Java 25/reactor prerequisites as the packaging lane, run the focused
JUnit method and retain its downloads in a fresh private directory:

```bash
./mvnw -B verify -Pplugin-packaging-tests,ci-plugin-packaging \
  '-Dit.test=ExternalPluginPackagedIT#externalSparxQeaV2JarExportsReviewedFilesAndRetainsDownloadsAcrossPluginChanges' \
  -Dtaxonomy.sparx.template=/absolute/path/to/empty.qea \
  -Dtaxonomy.sparx.qa.output=/absolute/path/to/new-private-output-directory
```

The template is read as input and its hash must remain unchanged. The output
directory receives one `<operationId>.qea` per completed operation and
`export-evidence.json`. Existing files are not overwritten. The supplied template
is used for `NEW_PROJECT`; `UPDATE_COPY` continues to exercise the controlled
imported synthetic model and its known local edit. This does not claim preservation
of every feature in an arbitrary production model.

## 3. Validate supplied files and optional EA observations through JUnit

Create a private manifest. Paths are relative to that manifest unless absolute:

```json
{
  "schemaVersion": 1,
  "template": "empty.qea",
  "exports": "outputs/export-evidence.json",
  "outputs": "outputs",
  "eaEvidence": "ea-evidence.json"
}
```

Omit `eaEvidence` when EA has not been run. An empty or broken evidence file is an
error, not a substitute for the omitted field. The check recomputes template and
output SHA-256, checks output sizes and SQLite headers, and requires both output
modes with unique operation identities. Header validation is a bounded format
sanity check, not a SQLite integrity or EA compatibility test.

Run the opt-in JUnit companion:

```bash
./mvnw -B verify -Pplugin-packaging-tests,ci-plugin-packaging \
  -Dit.test=SparxQeaProductEvidenceIT \
  -Dtaxonomy.sparx.product.evidence=true \
  -Dtaxonomy.sparx.product.manifest=/absolute/path/to/manifest.json
```

Explicitly enabling this companion without a manifest fails. It does not replace
the required packaging or product-driver suites. Its report is
`taxonomy-build/target/sparx-operator-evidence.json`:

| Situation | `status` | `realProductStatus` |
|---|---|---|
| Exact local files; no EA observations supplied | `FILE_EVIDENCE_VALIDATED` | `NOT_EXECUTED` |
| All files and complete operator EA observations are consistently bound | `OPERATOR_EVIDENCE_VALIDATED` | `NOT_EXECUTED` |
| Changed/missing files, failed observations or missing required coverage | JUnit failure | No passing acceptance report |

`realProductStatus` refers to execution by this harness. Operator observations are
separately labelled and must be assessed as externally supplied evidence; this
checker does not prove their authenticity or certify an EA release. It does not
modify `docs/qa/sparx-compatibility.json` or register a verified PCS provider.

### Recording actual EA observations

In an appropriately licensed EA environment, open each exact generated file,
verify the supported semantic subset, close and reopen it, and retain the actual
version/build, date, operator and execution log. Check GUIDs, element titles and
types, package hierarchy, relationship direction/endpoints and the specifically
claimed diagram behavior. Record losses rather than treating successful opening
as a full MDG/layout round trip. The Java bridge requires installed EA components;
see [Sparx's Automation connection documentation](https://www.sparxsystems.com/enterprise_architect_user_guide/17.2/add-ins___scripting/automation_connect_setup.html).

The external EA record has this shape. Replace placeholders with observed values
and include **every** operation from `export-evidence.json`, including the resumed
update-copy operation. The example shows one row only:

```json
{
  "schemaVersion": 1,
  "product": "Sparx Enterprise Architect",
  "version": "EXACT EA VERSION AND BUILD",
  "operator": "OPERATOR OR APPROVED EVIDENCE IDENTITY",
  "executionDate": "2026-11-06T12:00:00Z",
  "log": "ea-run.log",
  "logSha256": "SHA256_OF_THE_ACTUAL_LOG",
  "results": [
    {
      "operationId": "OPERATION_UUID_FROM_EXPORT_EVIDENCE",
      "outputSha256": "EXACT_OUTPUT_SHA256",
      "result": "PASSED",
      "checked": ["OPEN_IN_EA", "CLOSE_REOPEN", "SUPPORTED_SEMANTICS"],
      "knownLosses": []
    }
  ]
}
```

List only checks actually performed. Use a failed result when a required check
fails; the JUnit companion must then fail. It requires all three checks, complete
operation coverage, exact output hashes and the unchanged referenced log. Do not
put credentials or authenticated PCS URLs in the log.

## 4. PCS acceptance remains a separate gate

Sparx documents native [RDF/XML POST updates](https://sparxsystems.com/enterprise_architect_user_guide/17.2/the_model_repository/oslc_upd_resources.html).
Those documented endpoints alone do not establish Taxonomy's required atomic
scope compare-and-mutate, atomic resource absence, durable idempotency, durable
receipt lookup and complete versioned scope reads. A preflight GET followed by an
unconditional POST cannot supply these guarantees.

Before a live writer can be registered, provide the exact PCS/adapter version,
authorized test model and supported guarantee mechanism, then verify stale and
concurrent updates, competing creates, lost responses, identical-key replay,
restart/receipt recovery and scope consistency against the actual service. No
such endpoint or execution was available for the present implementation. A custom
HTTP provider tests Taxonomy's publication contract; it cannot certify the native
PCS service. Native QEA file generation must not register a verified PCS provider
or mark either product's execution as passed.

## Kurzanleitung auf Deutsch

Die verpflichtende Paketprüfung läuft über
`-Pplugin-packaging-tests,ci-plugin-packaging`. Sie baut die reale optionale JAR
und prüft beide Dateimodi, Übernahme einer lokalen Änderung, unveränderte
Eingabedateien, Downloads, Hashes, Neustart sowie den Zugriff nach Pluginentfernung.
Standardmäßig verwendet sie synthetische QEA-Dateien. Ein erfolgreiches Ergebnis
belegt den Taxonomy-Dateivertrag, keine Ausführung in Enterprise Architect.

Eine berechtigte eigene leere Vorlage wird mit
`-Dtaxonomy.sparx.template=/absolut/leeres-projekt.qea` übergeben. Mit
`-Dtaxonomy.sparx.qa.output=/absolut/neues-privates-verzeichnis` werden die erzeugten
Dateien und `export-evidence.json` separat aufbewahrt. Bestehende Dateien werden
nicht überschrieben. Die eigene Vorlage gilt für `NEW_PROJECT`; der Update-Test
behält sein kontrolliertes synthetisches Ausgangsmodell.

Für eine echte EA-Prüfung jede ausgegebene Datei in einer berechtigten Installation
öffnen, die zugesagten Eigenschaften prüfen und nach Schließen erneut öffnen.
Version, Betreiber, Zeitpunkt, Log, genaue Dateihashes und bekannte Verluste als
externe Beobachtungen dokumentieren. Danach den optionalen JUnit-Einstieg mit
`-Dtaxonomy.sparx.product.evidence=true` und
`-Dtaxonomy.sparx.product.manifest=/absolut/manifest.json` aufrufen.

Die reine Dateiprüfung liefert `FILE_EVIDENCE_VALIDATED`; vollständige konsistente
Betreiberbelege liefern `OPERATOR_EVIDENCE_VALIDATED`. Beide behalten für diesen
Harness `realProductStatus: NOT_EXECUTED`. Fehlende oder veränderte Dateien,
unvollständige Beobachtungen und fehlgeschlagene EA-Prüfungen lassen JUnit scheitern.
Die Authentizität fremder Beobachtungen und die PCS-Schreibgarantien werden damit
nicht bewiesen. Weder der bestehende Produktstatus noch die Registrierung
verifizierter PCS-Provider wird automatisch geändert.

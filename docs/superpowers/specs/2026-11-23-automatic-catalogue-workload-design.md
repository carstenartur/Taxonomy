# Verified catalogue reuse for one local analysis attempt

**Outcome: measurement harness retained; catalogue reuse not activated.** The corrected authenticated workload, full parity checks and scheduler census were completed and independently reviewed. Catalogue reuse remained conditional and was not selected from the measured profile. The later journal-write experiment was completed and rejected by its release gate. See [the final QA record](../../qa/2026-11-23-automatic-catalogue-performance.md).

The approved programme calls for less work between admission and local execution. This increment covers ordinary resumable REST and portfolio work with a server-resolved AnalysisModelBinding. A worker claiming a persisted job starts its own attempt. A source extension, distributed or streaming delivery, unbound legacy analysis, replay receipt, cancellation read and completion fallback keep their existing routes. No durable protocol, provider policy or export changes.

## Where the repeated work occurs

In the inherited production path, AnalysisContinuationService.frozenRequest obtains the archived tree and computes or checks Authority.catalogueHash. beginFrozen opens the archive again, constructs the tree, checks the saved authority and computes the input signature for store.begin. AnalyzeRequirementUseCase.analyze opens the archive again after the claim. Portfolio ProjectAnalysisContinuationService.begin encompasses the first two opens in one transaction. Each captureRevision verifies the generation and workbook/used overlay even when the one-entry retainedHierarchy cache hits. Each open still constructs every RootCatalogueSnapshot, validating parentage and provenance, then FrozenCatalogueView rebuilds the node and adjacency indexes. The detached graph and DTO conversion in TaxonomyService.getFullTree are additional work. Frozen overlay lookups read the view’s node metadata.

Authority.catalogueHash is SHA-256 of the length-prefixed tree JSON. The durable input hash frames request fields, the tree JSON and the relation fingerprint in a different order and then layers scope, language, model and extension identifiers. Reusing the former as an input to the latter would break existing journals. AnalysisEvidenceFingerprint’s counting and hashing passes preserve UTF-8 byte lengths and historical JSON writer semantics. Leave the signature routine and both passes intact. Reuse only the completed, tree-only hash for an exactly reverified view.

## Selected boundary

Create one opaque, immutable catalogue revision handle inside CatalogueSnapshotService. It retains its issuing service, CatalogueSourceIdentity, requested revision, complete CatalogueSourceJournal.Snapshot (including timestamp and every use/hash/length), selected and available root sets, and the validated FrozenCatalogueView. The workbook and overlay SHA-256 and lengths must be independently verified from the actual payload at **every** boundary. For admission the selection is Set.of(), meaning all roots in the retained definition, even when the analysis scope requests a subset. Pin the complete captured model binding and workspace/actor in the local analysis owner. The identity uses the model content hash only when there is no commit. The issuing service enforces catalogue role and exact configured-root policy each time. No client or persisted command contains the handle.

|---|---|---|
| Freeze an ordinary local bound request | Authorize workspace and resolve server model. Load generation and verify actual workbook and applicable overlay. Validate root records, model scope, root coverage and view. | Build one private admission DTO tree while the view is bound. Compute the authority hash using the same mapper. Close the read scope immediately. |

Repeat workspace, model, root, runtime, provider binding and scoring/relation compatibility checks as before. | Reuse the view identity and authority hash. Freshly verify the same generation, bytes, workspace/model/roots at the existing AdmittedCatalogue.open location before scoring or provider calls. | Bind the verified view in a new synchronous scope for that invocation. Entity-shaped and DTO reads continue creating independent, editable copies. |
| Failure or replay | Corrupt or missing sources fail closed. Valid changed provenance during one attempt conflicts. An accepted receipt bypasses execution as today. Close scopes on every exit. | No handle survives its owning Execution.close, is propagated to children, or is serialized for retry. |

Only pre-claim code owns the temporary DTO tree. The planned tree and output tree in LlmService remain execution-owned. Keeping the admission DTO tree through scoring would extend lifetime and make output mutation a potential source of changed evidence. The immutable view alone survives the claim.

Fresh reads matter in the real portfolio transaction. CatalogueSourceJournal.findRevision and retainedInput currently use EntityManager.find, so two Java calls can share a first-level entity. For the new verified path use uncached scalar JPQL projections of the revision fields and each relevant blob's length and actual payload. Validate references, all bounded lengths and use modes exactly as the journal does. Query the relations reference length as today; execution’s tree proof covers the workbook and used overlay bytes, and binds the full relations reference. Reuse the existing MAX_BYTES and actual SHA-verifying code. Do not use entity eviction, refresh unrelated writes, enable a query cache, or hold a lock across provider I/O. Read in the existing database transaction/isolation; the explicit second read at READ_COMMITTED must observe a competing committed replacement. Do not claim visibility beyond the database isolation contract. Add an independent-transaction execution test.

The service is the only handle issuer. Opening a newly captured view is limited to its first local construction; every later use requires the revalidation entry point. Each one-use observation also belongs to the observing thread. The knowledge handle is a content proof, not authority to execute a paid analysis. Only a live owning Execution (or its equivalent unforgeable execution-owned capability) may supply the proof to the synchronous use case. Check the owner thread, current checkpoint session, unconsumed/non-replay local execution, actor/workspace and full authoritative model before binding; reject a foreign supplied command model before replacing it. Reject closed, transferred or reused executions. A public analyze(command, VerifiedRevision) entry alone is insufficient. A hit occurs only on the same handle within the same invocation. Absent evidence and exceptions never populate a shared cache. The earlier hierarchy cache continues to share content-derived immutable nodes across requests as it already does. There is no attempt map, time-based expiry, new thread-local or stored serialized tree. A repository, workspace, principal, branch, commit/model hash, binding, definition, root selection or provenance difference cannot reuse the result. Normal later retries re-open the saved historical generation, even when the current catalogue has advanced.

The scalar proof is bounded to the actual READ_COMMITTED statements and their exact hash/length checks; do not claim one atomic point-in-time view across separate SELECTs. Use actual MVCC and the same outer EntityManager for stale-entity regressions, with valid XLSX/overlay inputs and independent committed replacements. Temporary payload arrays do not remain in VerifiedRevision. The provider-absent START path already reads one tree and observes policy twice; preserve it separately from the provider-backed two-tree admission path. Compare the actual store.begin hash against the historical mapper/framing, including non-ASCII and scope/reason/language, rather than only testing helper hashes.

## Alternatives and release criterion

A database revision ID cannot establish that the bytes still match it. A service-wide DTO cache risks mutable cross-run state and bypassing authority checks. One smaller alternative is retaining only the historical tree hash and tree during pre-claim validation, then fully reopening the archive in the use case. Choose that narrower increment if retaining the view through execution fails the identity/lifetime tests or brings no measured benefit. If fresh scalar payload reads make the complete path more expensive, keep the benchmark, keep all verification and compare the pre-claim-only alternative against baseline before shipping. There is no expectation of fewer source bytes or SQL statements merely from fewer view builds.

Use one authenticated, local, model-bound automatic job, with deterministic synthetic answers. Compare the candidate with the immediate pre-catalogue production head, preserving identical storage behavior. Fresh processes use copies of one cleanly closed pre-analysis HSQL/JGit seed so retained generation UUID/time/commit/model hashes remain identical. Count database executions and result rows, completed transactions, verified bytes, catalogue builds, physical provider-client attempts, reported tokens, duration and allocations. Compare semantic scores, directed typed relations, quotes, unresolved evidence and budgets. Count winning durable claims, actual private search passes and source-cohort advances separately from derived budget.slices. Use a small BR-only two-source rejection witness for normal CI and full eight-root default/bounded-source runs for application economics and opportunity counts. The full census includes VERIFY siblings, true zero-children NAVIGATE splits and a separately timed exact-transcript ready-wave shadow for fully funded root seeds. Shape or numeric headroom alone is not runtime admission proof. Keep the manual 254-boundary acceptance scenario and its assertions intact. Publish measured scope, counts and results with no claim about live model quality or latency. The existing hosted database, browser, security and coverage gates remain release conditions.

## Measurement-first execution decision

Task1 first establishes one actual model-bound automatic workload and attributes its work. The initial local source baseline is the completed packed-storage head8b16853, with packed writes false. That storage branch must pass its release gates and merge before the later stage is published. If the base advances, restack before comparative measurements and record the exact storage-equivalent source. The first baseline screen runs the cheap BR-only CI witness and one fresh default-full and bounded-full row from the same cleanly closed pre-analysis seed. These establish actual occurrence, semantics, resource outcomes and a single-run cost screen; they are not repeated-performance claims. Three alternating fresh baseline/candidate pairs belong to the selected candidate comparison once that candidate exists. Avoid pre-running three baseline sets merely to rerun them after candidate selection.

Include narrow actual-path counters for the newly identified inner-loop candidates: exact-key/compatible-query/fresh-absence populations and JDBC time for the exact compatibility predicate versus capacity COUNT; RelationWorkPlan snapshot/publication counts, elapsed time and source/task work; actual per-cohort replay and payload-binding work. These remain test observations, with no extra product query, cache or authority read. Physical database metadata/query plans are required for a subsequent index experiment. A source-only annotation audit does not establish deployed indexes or a database speedup. The automatic baseline determines whether catalogue reuse, a compatible-question index or incremental progress bookkeeping merits the next implementation. Tasks2/3 remain conditional; no view handle, query/index change, cursor, concurrent LLM calls or packet protocol is authorized merely by starting the harness.

The CI smoke remains inexpensive and in the existing default core application-test ownership. A new untagged AutomaticCatalogueWorkloadTest is assigned by the current default-core rule; retain that rule and inspect the source ownership catalogue. Do not add a shard tag or registry/profile change without a concrete need. Standalone full QA rows are explicit properties of the same harness, not the normal CI default. New helper/probe classes must not accidentally create an empty required JUnit source.

Keep the harness responsibilities in four focused test-only files: AutomaticCatalogueWorkloadTest owns authenticated seed, run and output assertions; AutomaticCatalogueWorkloadProbe owns narrow advice and scopes; AutomaticCatalogueWorkloadJdbc delegates JDBC calls and records actual counters; com.taxonomy.analysis.relations.CatalogueWorkloadShadow uses existing package access to the real prepare/ready/evaluate methods. The shadow is outside the measured worker interval and does not copy scheduler logic. This split creates no product API or additional JUnit test class.

# Stage 2 design · compact portfolio snapshot storage

Baseline 135de85, 23 November 2026. This design covers only req_analysis_snapshot.analysis_payload. It can be deployed without DDL, a database backfill or an externally visible format change. Journal result_json already uses the portable v1 codec. This stage does not change journal writers, snapshots' public DTOs, the three other portfolio payload columns or prompt behavior.

## Storage and trust

Write the exact String produced today by PortfolioJsonCodec.write(analysis). In enabled mode and only for up to 24,000,000 UTF-16 code units call the compatible fast-packing entry point PortableJsonPayloads.packFast(original, 24_000_000), using GZIP Deflater.BEST_SPEED within the same v1 frame. Retain the original small (<65,536 code units) and incompressible fallbacks, separate compression/hash passes, and all length/digest checks. Ordinary PortableJsonPayloads.pack and packSerialized keep their existing compression policy and output contracts; archives and journal writers do not switch compression effort. Above 24,000,000 or with writes off, store the original without attempting compression. The bound limits processing of the optional new representation. Plain legacy strings and ordinary portfolio writes retain their existing size behavior. The separate portable-export quota remains 24,000,000 decoded code units.

Readers distinguish the reserved, non-JSON prefix taxonomy-json-payload: at offset zero. Unknown family versions, malformed lengths/digests/encoding, truncated or oversized frames and tail or I/O errors fail before returning data. Real JSON strings containing the prefix (including quoted JSON scalar strings) follow the plain path. Null, empty, blank, invalid legacy JSON, missing recorded fields, embedded Unicode and exact original JSON text retain their existing meaning. Never reserialize a DTO to reconstruct stored evidence. The v1 integrity digest uses big-endian UTF-16 units. The separate continuation memo fingerprint intentionally uses little-endian UTF-16 units plus length over the actual stored characters, including a frame's header, Base64 and tail.

For a plain JDBC reader, sniff at most the family length using a PushbackReader and keep the existing streaming parser. Only a detected reserved-family frame may be materialized as a bounded stored String to use the existing PortableJsonPayloads.read(String,int,PayloadReader<T>). Its validated reader streams the expanded content and drains and verifies the entire frame even if the parser stops/ closes early. Do not call Clob.getSubString(), Clob.length(), or materialize plain CLOBs for this dispatch. The caller owns the locator and source reader; do not double-close them. When a continuation memo already matches, hash the complete stored stream directly, with no inflation. On a different fingerprint fully validate/bind the newly fetched content and publish only its own fingerprint after successful close/free; the earlier comparison never authorizes the new pass. Entry scope, memory limits, cancellation, fresh journal and question state, policy and authorization remain unchanged. A successful raw SQL/OID/locator mutation under the same ID is still detected. No metadata-only shortcut or asserted zero-CLOB hit.

## Compatibility and rollout

Reader-first deployment: the compatible release can contain both dual readers and the disabled writer. taxonomy.portfolio.snapshot.packed-writes=false is the default for every profile and remains false during mixed-version rollout. Before enabling explicitly, finish upgrading all readers of the same database (application/worker, report, backup, CLI/batch and integrations that read the raw column); retire old replicas, prohibit restarting old images against it, and verify a v1 export/reopen on this installation. Only then set TAXONOMY_PORTFOLIO_SNAPSHOT_PACKED_WRITES=true on desired writers. Mixed new write modes are supported; mixed capable and legacy readers require the option to stay false. No automatic activation based on process startup or database engine. Turning it off stops new frames; existing rows still require dual-read software. Rollback after first framed write must use at least this fully compatible dual-reader release. No in-place mass rewrite or automatic downgrade. Separate activation after compatible readers are deployed is required; a second code release is not required merely to expose the already-disabled writer.

Actual storage has no new DB objects. Use the existing PostgreSQL, SQL Server and Oracle matrix and file-backed HSQL. Include an opt-in packed-column smoke on each actual driver, with full and continuation reads plus a same-ID update. PostgreSQL must additionally prime the memo then perform equal-length lo_put on the same OID, and export equivalent plain/packed OID-backed values through the actual contributor with one-unpack equality. Preserve direct-locator replacement tests where the driver permits the mutation. A protected local filesystem, row ID or a Hibernate row version cannot substitute for content validation.

## Evidence and subsequent decision

The initial three-process default-compression v1 measurement reduced stored characters but regressed the measured write-plus-1–3-read mix. A separate phase-tagged JFR identified native deflate work and the decoded code-unit loop. Two isolated one-variable exploratory screens support Task 4: BEST_SPEED shortened encode p50 from the initial 931–944 ms to 292 ms and improved the paired HSQL write/read wall time, with larger frames and higher CPU/allocation than raw for low-read mixes; bulk conversion of complete UTF-16 pairs reduced default-v1 full/cold p50 to 146/156 ms. These screens do not establish combined performance. The shared PackedReader may copy complete pairs from its existing 8 KiB buffer, while the original nextByte/refill path remains responsible for boundary bytes and every length/CRC/SHA/tail check. Sticky failure, zero-length and closed-reader behavior, and inflater ownership remain unchanged. Verify the combined production implementation in three fresh paired processes and report remaining cold/full, CPU and allocation regressions. Keep the writer opt-in regardless of the screen.

Run an internal reversible prototype on representative early, middle and late snapshots if available. Collect actual stored characters, write CPU/allocation, p50/p95 cold/full and warm reads, mixed-workload timing and exact round trip. Advance a new frame family only if the incremental benefit is measured beyond noise and full compatibility is verified; its activation requires its own reader-first rollout. Do not ship a speculative new representation in this stage.

The reference experiment is complete and rejected for this stage. Three conservative policies and one separately measured direct combined policy passed 69 codec vector groups/subvectors and four real scoped-HSQL screens, each in a fresh 8-warmup/25-pair JVM. Combined references reduced the selected fast-v1 frame by28.75%, but all conservative write/read mixes regressed. The direct policy's7.7–19.8ms median mixed savings were below the control's run-to-run variation, while paired tails, CPU, allocation and full/cold reads worsened. It did not qualify for three-process promotion. Keep the product's existing v1 family and default-off writer. The QA report records the decision, source/build identity and all remaining workload/driver limits; unmeasured public/archive compatibility for the rejected experimental format is not a release claim.

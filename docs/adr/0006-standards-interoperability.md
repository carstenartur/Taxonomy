# ADR 0006: Reviewed standards interoperability

Status: Proposed — implementation and compatibility validation tracked in #926.

## Context

An exchange file, a remote tool resource, a requirement version, a private editing
revision and a Git architecture checkpoint are different identities. Treating a
download as successful publication, matching elements by name, or using the most
recent timestamp to resolve conflicts would lose both authority and auditability.

## Decision

Use one framework-neutral connector contract in `taxonomy-extension-api` and one
application workflow for ReqIF, OSLC RM and ArchiMate exchange. Capabilities are
explicit. A profile must not advertise remote publication unless it implements
conditional writes and durable per-resource outcomes. Vendor-specific adapters
remain optional implementations of this contract.

Every connection declares an authority mode and an exact repository, private
workspace, branch, external repository/configuration, mapping profile and version.
Its operation also freezes the Git checkpoint, semantic workspace revision and,
for requirements, the current project fingerprint. Actor comes from authenticated
server context. Credentials are deployment settings referenced by a remote profile
key, never part of exchange contracts, DSL, Git messages or integration events.

ReqIF requirements use the existing versioned project portfolio. They do not become
catalogue nodes. Architecture imports use typed DSL commands and stable namespaced
object identities. Imported view placements are presentation evidence, separately
identified from semantic elements and relations. Accepted extension data is stored
with the versioned model so a checkpoint can reconstruct the supported exchange
representation. The uploaded package and rejected decisions remain scoped audit
evidence; they are not replayed as the current model during export.

### Transaction and recovery

1. Preview records immutable input/context and proposed changes. It writes neither
   canonical model changes nor editor operations nor Git commits.
2. Apply locks the connection, then the workspace, then the selected project. It
   rechecks both revisions, validates decisions and the resulting dependency
   closure, and joins portfolio changes, identity mappings, the editor journal,
   operation status and the pending checkpoint intent in one ORM transaction.
3. The Git writer executes **after** that database transaction. The checkpoint ID
   derives from the integration operation ID. Its DSL, actor, rationale and parent
   were frozen during prepare. Restart retries the same intent and can recognize
   an already-written deterministic commit.
4. Completion links the integration checkpoint to the resulting Git version.
   A crash before this record does not require reapplying model changes. A rejected
   external/Git precondition is not converted to success.

There is no atomic transaction spanning the relational database, JGit and an
external requirements server. Pending/failure states and explicit retry exist
precisely because those boundaries can fail independently. File delivery retains
the generated bytes durably and never advances the confirmed external baseline.

### Conflicts and deletion

Compare the last accepted external/internal pair with the incoming external data
and current internal authority. Disjoint field changes can be combined. An
intersecting edit, identity reuse or deletion-versus-edit needs an explicit review
decision and rationale. A normal acceptance cannot silently resolve a conflict.

Only a complete external file scope in mirror/bidirectional mode can propose
deletion. Deletion is a candidate requiring an individual decision and valid
dependency closure. Remote reads are bounded partial observations; missing pages,
404/403 responses and timeouts never manufacture deletion candidates.

### Version boundaries

A model-changing accepted import is an explicit integration version boundary and
creates one checkpoint for the reviewed batch. An unchanged import creates no
redundant Git commit. Link-only operations, previews, discovery, cancellation and
file exports create no Git commit. Ordinary editor commands retain ADR 0005's
durable semantic journal behavior and create no Git commit.

The integration batch is recorded as `VERSION_IMPORT`. Its portfolio changes must
not be undone by a DSL-only inverse. Version compare/restore remains the explicit
cross-model recovery path; ordinary editor undo/redo remains semantic and append-only.

## Consequences

Profiles and loss reports define a supported subset, not a claim that all versions
of every vendor tool interoperate. Pinned schemas and independent fixtures prove
format contracts. Installed product import/export runs must separately record tool
versions, fixture fingerprints and observed results before product compatibility is
claimed. Unsupported constructs fail or require a reviewed mapping; no approximate
relationship fallback is allowed.

Editor projections rebuild from the durable DSL; checkpoint projections rebuild
from the selected Git version. Requirement search derives from scoped portfolio
versions. Integration mappings and events are durable synchronization evidence,
not a second authoring model or an authoritative search index.

This extends ADR 0005's separation of semantic editing and Git versions. It also
keeps the audio-analyzer principle: persist fine-grained operational evidence
durably, and create Git versions only at intentional application boundaries.
